# Issue #20 review

Mobile access now has a persisted port setting, defaulting to 8787 and validating the full TCP range 1–65535. Editing the field only stages a value: focus changes, Return, and view dismissal do not save or restart anything. The explicit Apply button is enabled only for a valid changed value. Applying restarts the local server, verifies its loopback listener, and reconfigures an enabled Tailscale Serve proxy. A failed local bind restores the previous saved port and listener; a Tailscale update failure clearly reports that local access changed while Secure Mobile Access did not.

## Manual checks

1. Enable Mobile Access. Type a valid unused port without clicking Apply, then click elsewhere and press Return in the field. Confirm the caption says the change is staged, Apply remains enabled, the saved/current port remains 8787, and the existing link still works on 8787.
2. Click Apply. Confirm the control shows a restarting state, then reports success; Online returns and the LAN URL and QR code use the new port.
3. Enter an empty value, 0, 65536, and text. Confirm validation is visible, Apply is disabled, and the current listener remains unchanged. Enter the current port and confirm Apply is disabled with a clear current-port caption.
4. Apply a port already occupied by another process. Confirm Rashun reports the bind failure, restores the previous port, and the previous link becomes reachable again.
5. With Secure Mobile Access disabled, apply a new port. Confirm the LAN/QR URL includes it and no Tailscale Serve command/configuration changes.
6. With Secure Mobile Access enabled, apply a new port. Confirm the advertised/QR URL remains `https://<tailnet-name>` and `tailscale serve status --json` shows `/` proxying to `http://127.0.0.1:<new-port>`.

## Port-change behavior found in the implementation

- Applying posts the existing settings-change notification. `AppDelegate.updateSyncServerLifecycle()` cancels both the current `RashunSyncServer` task and the outbound `PeerSyncService` task, then creates replacements. The server binds `0.0.0.0:<configured-port>`; outbound desktop sync restarts using its unchanged saved peer-address list.
- There is no live connection or URL migration protocol. The old server service task is cancelled, but the app has no explicit per-connection drain/migration handling; requests using the old LAN port are not redirected. The mobile web app has no persistent socket: it performs same-origin HTTP fetches and polls every 60 seconds, so an open/copied old LAN URL remains on the stale origin and its later refreshes fail until the user opens the new URL. The currently displayed QR/link recomputes with the new port while retaining its current pairing code.
- Peer credentials, mobile browser credentials/cookies, push subscriptions, and peer records are not revoked or rewritten by a port change. Cookies are not scoped by TCP port, but the code does not navigate an already-open LAN browser tab to the new port. HTTPS Tailscale clients keep the same public `https://<tailnet-name>` origin and can resume after the proxy is updated.
- Saved desktop peer addresses are literal URLs in `SyncRepository`. Changing this Mac's port does not rewrite this Mac's saved URLs for other peers, and it does not notify remote peers to replace the saved return URL they hold for this Mac. Consequently, remote peers with this Mac's old LAN URL continue trying the stale port until they are reconnected or another saved address succeeds. The app does not run its available Bonjour advertiser, so there is no app-side Bonjour rediscovery/failover here.
- With Secure Mobile Access disabled (or Tailscale unavailable), the advertised mobile/desktop URL and QR link use `http://<LAN-address>:<configured-port>`. Applying a port does not invoke Tailscale in that state.
- With Secure Mobile Access enabled, the local server still binds plain HTTP on `0.0.0.0:<configured-port>`, while the advertised/QR URL is `https://<tailnet-DNS-name>` on implicit port 443. Rashun runs `tailscale serve --bg <configured-port>` and verifies that the root handler proxies to `http://127.0.0.1:<configured-port>`. Disabling Secure Mobile Access runs `tailscale serve --https=443 off` only for a route marked as managed by Rashun.
- A root Serve handler pointing anywhere other than the configured loopback port is treated as a conflict. Rashun will not overwrite a pre-existing conflicting handler through the HTTPS toggle. On a port apply, only a previously detected enabled Rashun handler is reconfigured; unavailable/unprobed Tailscale and externally managed/conflicting handlers are not changed.
- Not handled: automatic redirect/discovery from the old LAN port, updates to remote peers' saved return URLs, navigation of already-open LAN browser tabs, or automatic repair of Tailscale configuration after a reported Tailscale command/verification failure.
